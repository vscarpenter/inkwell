# Repository Guidelines

## Project Structure & Module Organization

Inkwell is a pure-CSS design system with no package manager, framework, or build step. The canonical source files are `inkwell-tokens.css` (single-declaration `:root` custom properties — `light-dark()` per mode, `color-mix()` derived tints — plus `color-scheme` mode machinery) and `inkwell-components.css` (base reset, components, layout helpers, a11y). `inkwell.css` is the canonical entry: it imports the tokens file unlayered and the components file into `@layer inkwell`. `tokens.css` is a deprecated one-line alias of `inkwell.css` (removal slated for 4.0). Consumers link `inkwell.css` from `<head>` and the whole tree resolves. `inkwell-theme.css` is the Tailwind v4 entry — it imports the same two source files, wraps components in `@layer components`, and declares `@theme` aliases plus a `@custom-variant dark` block. See [`TAILWIND.md`](TAILWIND.md) for the Tailwind path. Keep all five CSS files side by side. `tokens.json` mirrors `inkwell-tokens.css` for external tooling and is generated by `scripts/build-tokens-json.mjs` — do not edit by hand. Re-run `node scripts/build-tokens-json.mjs` after touching `inkwell-tokens.css`. The releases section of `examples/changelog.html` and the `data-inkwell-version` footer stamps on every example page are likewise generated from `CHANGELOG.md` by `scripts/build-changelog-html.mjs` — re-run it after editing `CHANGELOG.md`, and edit the changelog page only outside its BEGIN/END markers. Every deployed page also has one `data-inkwell-deployed` `<time>` placeholder; `scripts/stamp-deployment.mjs --check` validates the checked-in markers, while the Pages workflow stamps only its artifact copy. CI runs `--check` for generated sources and fails on drift. Manual review surfaces live in `index.html`, `preview.html`, and `examples/`. The `variants/` directory holds four palette-override CSS files (clay, sage, burgundy, azure). Each loads on top of inkwell.css to swap the brand layer; they never restate component CSS.

## Build, Test, and Development Commands

There is nothing to install or compile. Open files directly in a browser:

```bash
open index.html              # starter template and theme toggle
open preview.html            # full component showcase
open variants/compare.html   # side-by-side palette comparison
```

GitHub Pages deploys `examples/` on every push to `main`. The workflow checks out full history, `cp`s the five canonical files into `examples/` and the four variant files into `examples/variants/`, then stamps the artifact footer as `vX.Y.Z+build.N · Deployed Mon D, YYYY`; `N` is the repository commit count. Checked-in pages keep the base semantic version and `Deployment pending` placeholder so workflow runs never create commits or recurse.

## Coding Style & Naming Conventions

Use two-space indentation in CSS and HTML. Route component styling through CSS custom properties instead of hard-coded literals. New work should use `--accent`, `--ivory`, `--paper`, `--slate`, and related tokens from `inkwell-tokens.css`. Variant files in `variants/` also use `--accent` — they override the brand-layer tokens to switch the palette. Preserve the design invariants in `DESIGN_SYSTEM.md`: 1.5px borders via `--border`, one saturated accent, platform fonts only, and light/dark values for saturated tokens. When editing source CSS, edit `inkwell-tokens.css` (for tokens / dark cascade) or `inkwell-components.css` (for component / type / layout / a11y rules); never edit `tokens.css` or `inkwell.css` (aggregators). For Tailwind-exposed tokens, also surface them in `inkwell-theme.css`.

## Testing Guidelines

Verification is visual. After changing CSS or markup, review `preview.html` in light, dark, and auto theme modes. If your change touches the Tailwind v4 path, also review `examples/tailwind.html` and the cascade-order check in [`TAILWIND.md`](TAILWIND.md). If color or palette behavior changed, also review `variants/compare.html`. Prefer checking on a 2x display because the 1.5px border is retina-first and may render as 1px on non-retina screens.

## Commit & Pull Request Guidelines

Recent commits use short imperative subjects, for example `Surface agent-instructions.md from the README` and `Make navigation between example pages explicit`. Keep each commit focused on one concern. PRs should describe the visual or API impact, list touched surfaces, include screenshots for visual changes, and update `DESIGN_SYSTEM.md`, `README.md`, or `CHANGELOG.md` when behavior or public usage changes.

## Agent-Specific Instructions

Read `DESIGN_SYSTEM.md` before extending components, `TAILWIND.md` before touching the Tailwind v4 integration, and `agent-instructions.md` before using Inkwell in another project. Do not add build tooling, package metadata, framework wrappers, webfonts, or generated assets unless explicitly requested.

When changing hard rules, anti-patterns, install steps, or component lists, update in the same PR:

- `agent-instructions.md`
- `DESIGN_SYSTEM.md` (§4 anti-patterns, §6 quick start as applicable)
- `README.md` quick start (if install changes)
- `CLAUDE.md` (if repo-editing rules change)
