# Repository Guidelines

## Project Structure & Module Organization

Inkwell is a pure-CSS design system with no consumer package manager, framework, or build step. The canonical source files are `inkwell-tokens.css` (single-declaration `:root` custom properties — `light-dark()` per mode, `color-mix()` derived tints — plus `color-scheme` mode machinery) and `inkwell-components.css` (base reset, components, layout helpers, a11y). `inkwell.css` is the canonical entry: it imports the tokens file unlayered and the components file into `@layer inkwell`. `tokens.css` is a deprecated one-line alias of `inkwell.css` (removal slated for 4.0). Consumers link `inkwell.css` from `<head>` and the whole tree resolves. `inkwell-theme.css` is the Tailwind v4 entry. `inkwell-interactions.js` is an optional framework-free companion for tabs, carousel controls, and declarative dialogs. Keep all six distributable files side by side. `tokens.json` mirrors `inkwell-tokens.css` and is generated by `scripts/build-tokens-json.mjs`. `component-manifest.json` is the public component contract; it generates the marked region in `examples/components.html` via `scripts/build-components-reference.mjs`. The releases region of `examples/changelog.html` and `data-inkwell-version` stamps are generated from `CHANGELOG.md`. Every deployed page also has one `data-inkwell-deployed` placeholder; Pages stamps only its artifact copy. CI runs every generated-file, contrast, repository-contract, and browser-smoke check. Manual review surfaces live in `index.html`, `preview.html`, `examples/components.html`, and `examples/`. The `variants/` directory holds four override-only palettes.

## Build, Test, and Development Commands

There is nothing to install or compile. Open files directly in a browser:

```bash
open index.html              # starter template and theme toggle
open preview.html            # full component showcase
open examples/components.html # generated adoption reference
open variants/compare.html   # side-by-side palette comparison
```

GitHub Pages deploys `examples/` on every push to `main`. The workflow checks out full history, runs all static contract/generation gates, copies the six distributable files into `examples/` and the four variant files into `examples/variants/`, then stamps the artifact footer as `vX.Y.Z+build.N · Deployed Mon D, YYYY`; `N` is the repository commit count. Checked-in pages keep the base semantic version and `Deployment pending` placeholder so workflow runs never create commits or recurse.

## Coding Style & Naming Conventions

Use two-space indentation in CSS and HTML. Route component styling through CSS custom properties instead of hard-coded literals. New work should use `--accent`, `--ivory`, `--paper`, `--slate`, and related tokens from `inkwell-tokens.css`. Variant files in `variants/` also use `--accent` — they override the brand-layer tokens to switch the palette. Preserve the design invariants in `DESIGN_SYSTEM.md`: 1.5px borders via `--border`, one saturated accent, platform fonts only, and light/dark values for saturated tokens. When editing source CSS, edit `inkwell-tokens.css` (for tokens / dark cascade) or `inkwell-components.css` (for component / type / layout / a11y rules); never edit `tokens.css` or `inkwell.css` (aggregators). For Tailwind-exposed tokens, also surface them in `inkwell-theme.css`.

## Testing Guidelines

Run every zero-dependency check (`build-tokens-json --check`, `build-changelog-html --check`, `build-components-reference --check`, `stamp-deployment --check`, `check-contrast`, `check-system-contract`) plus `git diff --check`. Run the ephemeral Playwright suite for HTML/CSS/interaction changes. Then review `preview.html` in light, dark, and auto; `examples/tailwind.html` for Tailwind changes; and `variants/compare.html` for palette changes. Prefer a 2x display because the 1.5px border is retina-first.

## Commit & Pull Request Guidelines

Recent commits use short imperative subjects, for example `Surface agent-instructions.md from the README` and `Make navigation between example pages explicit`. Keep each commit focused on one concern. PRs should describe the visual or API impact, list touched surfaces, include screenshots for visual changes, and update `DESIGN_SYSTEM.md`, `README.md`, or `CHANGELOG.md` when behavior or public usage changes.

## Agent-Specific Instructions

Read `DESIGN_SYSTEM.md` before extending components, `TAILWIND.md` before touching the Tailwind v4 integration, and `agent-instructions.md` before using Inkwell in another project. Do not add build tooling, package metadata, framework wrappers, webfonts, or generated assets unless explicitly requested.

When changing hard rules, anti-patterns, install steps, or component lists, update in the same PR:

- `agent-instructions.md`
- `DESIGN_SYSTEM.md` (§4 anti-patterns, §6 quick start as applicable)
- `README.md` quick start (if install changes)
- `CLAUDE.md` (if repo-editing rules change)
